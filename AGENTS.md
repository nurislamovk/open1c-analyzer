# Правила работы с Open1C Analyzer

## 1. Среда

- ОС: Windows.
- Оболочка: PowerShell.
- Python и Python-инструменты запускать через `uv`.
- Репозиторий: `C:\Users\Kostya\GitHub\open1c-analyzer`.

## 2. Основная проверка проекта

```powershell
uv run open1c check
```

Проверка должна полностью проходить все этапы:

- Ruff format;
- Ruff autofix/verify;
- mypy;
- pytest.

## 3. Критерий завершения задачи

Никогда не считать задачу законченной только потому, что прошел Ruff.
Задача закончена только после успешного полного `uv run open1c check`
и функциональной проверки.

## 4. Размер функциональных блоков

Работать крупными законченными функциональными блоками, без микрокоммитов.

## 5. Git

- Не делать commit автоматически в процессе разработки.
- Сначала завершить функциональность.
- Выполнить полный `uv run open1c check`.
- Выполнить реальный функциональный тест.
- Посмотреть `git diff`, включая новые файлы.
- Делать commit и push только после явного разрешения пользователя
  на соответствующее действие.

## 6. Проекты 1С и границы анализа

| Проект | Каталог исходников | Связь |
| --- | --- | --- |
| `TMS_UNF` | `C:\Projects\TMS` | Основная конфигурация TMS |
| `TMS_EXT` | `C:\Projects\TMSExt` | Расширение `TMS_UNF` |
| `SGK_BP` | `C:\Projects\SGK\BP` | Отдельная независимая конфигурация другого проекта |

`TMS_EXT` является расширением `TMS_UNF`. При совместном анализе использовать
`--include` только в рамках связанной конфигурации и ее расширения, например:

```powershell
uv run open1c project analyze TMS_EXT --include TMS_UNF
```

Никогда не смешивать граф или анализ `SGK_BP` с `TMS_UNF`/`TMS_EXT`
через `--include`.

Если впоследствии появится `SGK_EXT`, считать его расширением `SGK_BP`.

## 7. Назначение анализатора и регрессионные тесты

Open1C Analyzer — статический анализатор экспортированных исходников 1С.
При изменении parser/resolver/retrieval/ask обязательно добавлять
регрессионные тесты.

## 8. Реальные функциональные проверки

Не ограничиваться unit tests. Использовать существующие проекты 1С
как функциональные тесты, соблюдая границы проектов из раздела 6.
Проверять реальное поведение затронутой функциональности.

## 9. Входные данные только для чтения

Не изменять исходники в каталогах:

- `C:\Projects\TMS`;
- `C:\Projects\TMSExt`;
- `C:\Projects\SGK\BP`.

Это входные данные анализатора, а не исходный код Open1C Analyzer.
